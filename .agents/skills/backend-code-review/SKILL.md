# 백엔드 코드 리뷰

## 개요

정확성, 금융 데이터, 보안, 계약 또는 유지보수성을 위협하는 실행 가능한 결함을 찾는다. 요약보다 증거를 먼저 검토하고, 테스트 통과를 머지 안전성과 동일하게 보지 않는다.

## 리뷰 절차

1. `AGENTS.md`, 기준 명세와 전체 diff를 읽는다. 동작 확인에 필요한 주변 운영 코드와 테스트도 살펴본다. API·코드 규칙은 `docs/code-style.md`, 테스트 증거는 `docs/testing.md`, 버전·모듈은 실제 Gradle 파일에서 확인하며 관련 없는 문서는 읽지 않는다.
2. 의도한 동작과 인수 조건을 확인한다. 검증할 수 없는 범위는 추측하지 않고 검증 공백으로 표시한다.
3. 다음 순서로 검토한다.
   - **아키텍처:** `api,batch -> core` 방향을 지키고 도메인 규칙을 컨트롤러, 배치 단계와 조율 서비스에서 분리한다.
   - **금융 정확성:** 기준일, 정밀도, 반올림, 누락 데이터, 0·음수, 경계값과 EOD 의미를 확인한다.
   - **트랜잭션과 데이터:** 원자성, outbox, 멱등성, 잠금, N+1, PostgreSQL/H2 차이와 재시도 영향을 확인한다.
   - **API 계약:** 응답 래퍼, `record`, 유효성 검사, 오류 코드, 인가, 페이지네이션, REST Docs와 OpenAPI 호환성을 확인한다.
   - **보안과 운영:** 비밀값 노출, OAuth2 전제, 소유권 검사, 로깅, 시간 제한과 장애 격리를 확인한다.
   - **테스트:** 변경 동작과 실패 경로를 단순 mock이나 정상 경로만이 아닌 의미 있는 테스트가 검증하는지 확인한다.
4. 각 발견 사항이 검토 중인 변경에서 새로 발생하거나 드러난 문제인지 확인한다. 파일과 줄 위치를 좁게 지정한다.
5. 요약보다 발견 사항을 먼저 작성한다. 실행 가능한 발견 사항이 없으면 명확히 밝히고 남은 검증 공백을 적는다.
6. 리뷰는 항상 읽기 전용으로 수행한다. 코드는 사용자가 수정 작업을 별도로 요청한 경우에만 변경하고, `code-review.md`는 사용자가 명시적으로 요청한 경우에만 작성한다.

## 발견 사항 형식

다음 심각도를 사용한다.

- 🔴 **차단** — 정확성, 보안, 데이터 손실, 계약 파손 또는 확실한 운영 장애로 머지 전에 반드시 수정한다.
- 🟡 **중요** — 신뢰성, 성능, 유지보수성 또는 테스트 누락 위험 때문에 수정을 강력히 권고한다.
- 🟢 **경미** — 출시를 막지 않는 선택적이고 국소적인 개선이다.

각 발견 사항에 다음을 포함한다.

1. `[심각도] 실행 가능한 제목`
2. `위치: 경로:줄`
3. 구체적인 근거와 발생 상황
4. 사용자, 데이터 또는 운영 영향
5. 가장 작은 안전한 수정 방향

마지막에는 사용한 정확한 검증 증거와 함께 `머지 차단`, `조건부 머지` 또는 `머지 가능`으로 판정한다.

## 흔한 실수

- 결함 대신 diff 내용을 다시 설명한다.
- 사용자나 엔지니어링 영향이 없는 스타일 선호를 지적한다.
- 테스트가 실제로 무엇을 검증하는지 확인하지 않고 통과 결과만 신뢰한다.
- 변경과 관계없는 기존 코드를 차단 문제로 보고한다.
- 확인하지 못한 통합 증거를 밝히지 않고 머지 여부를 판정한다.
